# Практика 9: ручное тестирование API в Postman

На занятии запускаем обычное приложение и отправляем восемь запросов по одному кнопкой **Send**. Статус, заголовки и тело ответа проверяем вручную по [тест-кейсам](test-cases.md). URL уже указан в каждом запросе коллекции.

## 1. Запустить приложение

Нужны Java 21, Maven и настольный Postman. Первую сборку выполните до занятия: Maven может потребоваться интернет для загрузки зависимостей.

Из терминала:

```bash
cd /Users/akylbek/IdeaProjects/su/su-microservices
mvn spring-boot:run
```

Либо в IntelliJ IDEA откройте `src/main/java/kz/su/currency/CurrencyApplication.java` и запустите `main` через **Run**. Выберите JDK 21 и рабочий каталог — корень проекта. Используйте один способ запуска, чтобы не занять порт вторым экземпляром.

Дождитесь сообщения `Started CurrencyApplication`. Приложение слушает `http://localhost:8080`, БД хранится в `data/currency` и сохраняется после остановки. Используются обычные настройки проекта. Если на порту 8080 уже работает приложение, остановите прежний экземпляр.

## 2. Открыть коллекцию в Postman

1. Нажмите **Import**.
2. Выберите только [currency-api.postman_collection.json](currency-api.postman_collection.json) из этой папки.
3. Откройте коллекцию **QA 09 — Currency API — ручная проверка**.
4. Выберите **No environment**, если ранее было выбрано окружение старого стенда. Если старая коллекция с 30 запросами осталась в Postman, удалите её вручную, чтобы не перепутать наборы.
5. Откройте API-01. Метод — POST, адрес — `http://localhost:8080/api/v1/conversions`.
6. На вкладке **Body** уже выбрано raw → JSON. В **Headers** указан `Content-Type: application/json`. Токен авторизации не нужен.
7. Нажмите **Send** и сравните ответ с ожиданием в описании запроса и тест-кейсах.

Автоматических assertions в коллекции нет: вкладка Test Results может быть пустой, это нормально. Результат теста определяет преподаватель или студент по фактическому ответу. Запускать Collection Runner не требуется.

## 3. Показать тесты на занятии: 20–25 минут

Начните с контракта: POST принимает from, to и amount, возвращает курс и результат. Успешный расчёт даёт 200; неверный ввод — 400. Ноль допустим. Подробнее — в [спецификации](../specification.md).

| Порядок | Запрос | Что показать |
| --- | --- | --- |
| 1 | API-01: USD → USD, 12.345 | 200; rate=1, convertedAmount=12.35; обе даты null. Проверяем округление и все поля ответа |
| 2 | API-02: `" usd "` → `"840"` | 200; валюты нормализованы в USD, результат тот же. Пробелы, регистр, цифровой код |
| 3 | API-03: amount=0 | 200, convertedAmount=0. Нижняя допустимая граница |
| 4 | API-04: нет amount | 400 INVALID_REQUEST. Обязательность поля |
| 5 | API-05: amount=-0.01 | 400 INVALID_REQUEST. Недопустимое значение |
| 6 | API-06: from=ZZZ | 400 INVALID_CURRENCY. Проверка ISO-кода |
| 7 | API-07: повреждённый JSON | 400 INVALID_REQUEST. Синтаксическая ошибка не должна давать 500 |
| 8 | API-08: 100 USD → KZT | 200, положительный курс и сумма, заполненные даты. Реальная конвертация через источник или кеш |

Перед Send предложите студентам назвать ожидаемый HTTP-код и результат. После отправки покажите в области ответа статус, Headers → Content-Type и Body → JSON. У успеха должны быть from, to, amount, rate, convertedAmount, rateDate, fetchedOn. У ошибки проверьте status, code, непустой detail и отсутствие convertedAmount.

В API-01 ожидается численно такой ответ:

```json
{
  "from": "USD",
  "to": "USD",
  "amount": 12.345,
  "rate": 1,
  "convertedAmount": 12.35,
  "rateDate": null,
  "fetchedOn": null
}
```

JSON может отображать rate как 1.0000000000 — значение то же. Наличие HTTP 200 само по себе ещё не подтверждает верную сумму. И наоборот, ожидаемый 400 в негативном кейсе означает Pass, если тело ошибки тоже соответствует контракту.

## 4. Учесть доступность курсов

API-01…07 работают без обращения к внешнему источнику. В API-08 используется публичный ExchangeRate-API либо курсы USD/KZT, уже загруженные сегодня. Интернет нужен для первой загрузки или обновления кеша. Фиксированного ожидания «курс 500» больше нет: курс реальный и меняется.

Если API-08 вернул 503 PROVIDER_UNAVAILABLE, источник недоступен или вернул некорректные данные. Зафиксируйте Blocked для позитивного кейса; остальные семь демонстрируются независимо. Старые данные не удаляйте. Для этого занятия SQL и управление кешем не нужны.

## 5. Записать результат и остановить приложение

Заполните [лист результатов](test-cases.md#лист-результатов): ID, фактический HTTP-код, важные поля, Pass/Fail/Blocked. Для неуспешной проверки сохраните запрос и ответ.

В конце нажмите **Ctrl+C** в терминале либо **Stop** в IDE. После изменения кода перед запуском из IDE убедитесь, что проект пересобран.

Если Postman пишет Connection refused, проверьте, что приложение запущено и порт равен 8080. При 415 проверьте Body → raw → JSON и Content-Type. При ошибке старта приложения смотрите консоль запуска.
