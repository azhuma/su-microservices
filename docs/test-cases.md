# Минимальный набор ручных тест-кейсов

Это инструкции для ручного тестирования работающего REST-сервиса с настройками по умолчанию. Тестировщик выполняет шаги, сравнивает HTTP-ответ и состояние БД, затем записывает фактический результат и статус «пройден/не пройден». `mvn test` запускает юнит-тесты и проверки схемы H2 в памяти и не выполняет эти кейсы.

## Почему выбран этот набор

Двенадцать кейсов покрывают разные пользовательские и инфраструктурные пути: форматы кодов и расчёт, одинаковые валюты, границы точности, первая загрузка и повторное чтение, обновление устаревших/неполных данных, разные даты публикации и загрузки, неверный запрос, отсутствие котировки, сбой источника, откат записи и перезапуск. Внутри кейса перечислены представители одного правила, чтобы не дублировать подготовку для каждого значения. Источник публичный; его ошибочные JSON-ответы проверяются юнит-тестом парсера. Это минимальная проверка основных требований, без полного перебора всех валют и нагрузочных сценариев.

## Подготовка стенда

Нужны Java 21, Maven, интернет для загрузки курсов, `curl` либо Postman и браузер. Из корня проекта запустить приложение одной командой:

```bash
mvn spring-boot:run
```

Можно также запустить `CurrencyApplication` из IDE. Порт — `8080`, источник — `https://open.er-api.com/v6/latest/USD`, файловая БД — `./data/currency`. Подготовка файлов источника, отдельный HTTP-сервер и параметры запуска не нужны.

Для SQL-проверок открыть встроенную консоль `http://localhost:8080/h2-console`: драйвер `org.h2.Driver`, JDBC URL `jdbc:h2:file:./data/currency`, пользователь `sa`, пароль пустой. Консоль работает внутри приложения и подключается к той же БД. После входа выполнить `SET TIME ZONE 'Asia/Almaty';`.

Далее T означает сегодняшнюю дату в Asia/Almaty; `CURRENT_DATE` в SQL возвращает T. D — UTC-дата обновления набора из `time_last_update_unix` источника. Кейсы с SQL изменяют кеш курсов локального приложения; его восстановление описано в соответствующих шагах. Перед каждым кейсом проверить его предусловие. Отключение интернета не мешает запросам к `localhost`; после сетевых проверок восстановить подключение.

Основной запрос:

```bash
curl -i -X POST http://localhost:8080/api/v1/conversions \
  -H 'Content-Type: application/json' \
  -d '{"from":"USD","to":"KZT","amount":100}'
```

Для остальных шагов заменить тело JSON. Состояние БД проверять запросом:

```sql
SELECT currency_code, numeric_code, kzt_per_unit, rate_date, fetched_on
FROM exchange_rate ORDER BY currency_code;
```

Для расчётных кейсов взять `kzt_per_unit` из сохранённого набора: `U` — USD, `K` — KZT (равен 1), `R` — RUB, `E` — EUR. Ожидаемый курс A → B равен `kzt_per_unit(A) / kzt_per_unit(B)`, отображается с 10 знаками и HALF_UP. Сумма вычисляется по неокруглённому курсу с точностью DECIMAL128, затем округляется HALF_UP до разрядности целевой валюты. Числа публичного источника меняются; фиксированного ожидания «500 KZT за USD» нет. Только TC-04 использует заданные через SQL значения для точного воспроизведения ошибок округления.

При необходимости сверить нормализацию с ответом источника:

```bash
curl -sS 'https://open.er-api.com/v6/latest/USD'
```

Для совпадающего timestamp ожидается `kzt_per_unit(X) = rates[KZT] / rates[X]` с 18 знаками и HALF_UP. Если источник успел обновиться, использовать значения уже сохранённого набора, а не сравнивать котировки разных публикаций.

## TC-01. Основной расчёт и форматы ISO-кодов

Предусловие: источник доступен; в БД полный набор, загруженный сегодня (при необходимости сначала выполнить основной запрос).

Шаги: отправить USD → KZT, 100; затем `840` → `398`, 100; затем `" usd "` → `"398"`, 100.

Ожидается: каждый ответ 200, `from=USD`, `to=KZT`; курс равен U/K с 10 знаками, сумма — 100×U/K с 2 знаками. Результаты и даты трёх запросов совпадают, `rateDate=D`, `fetchedOn=T`; сохранённый набор не изменился.

Почему выбран: основной пользовательский путь, нормализация и равенство форматов кодов.

## TC-02. Обратное направление и базовая валюта

Предусловие: свежий полный набор в БД.

Шаги: отправить KZT → USD, 500; USD → RUB, 2; RUB → USD, 180.

Ожидается: 200; соответственно курс/сумма K/U и 500×K/U, U/R и 2×U/R, R/U и 180×R/U. Курсы округлены до 10 знаков, суммы — до 2; в БД KZT имеет `kzt_per_unit=1`. RUB является обычной валютой кросс-курса.

Почему выбран: обнаруживает перепутанное деление и неверную нормализацию базового KZT; дополнительно проверяет конвертацию RUB.

## TC-03. Одинаковые валюты без данных и сети

Предусловие: выполнить `DELETE FROM exchange_rate;`; временно отключить интернет.

Шаги: отправить `"usd"` → `"840"`, 12.345; проверить БД; восстановить интернет.

Ожидается: 200, курс `1.0000000000`, сумма `12.35`, обе даты null. БД пуста; недоступность источника не мешает ответу.

Почему выбран: отдельный путь, которому не нужны котировки.

## TC-04. Округление, ноль и большая сумма

Предусловие: свежий полный набор в БД.

Перед запросами задать в H2 Console контролируемые курсы:

```sql
UPDATE exchange_rate SET kzt_per_unit = 1
WHERE currency_code IN ('USD', 'JPY', 'KWD');
UPDATE exchange_rate SET kzt_per_unit = 3 WHERE currency_code = 'EUR';
```

Для округления суммы в USD использовать EUR → USD с суммой `0.335`: курс 3 даёт точное значение `1.005` до округления.

Отправить каждый запрос из таблицы и сравнить ответ 200:

| from → to | amount | Ожидаемая сумма | Что проверяет |
| --- | --- | --- | --- |
| USD → JPY | 2.5 | 3 | 0 дробных разрядов и HALF_UP вместо HALF_EVEN |
| EUR → USD | 0.335 | 1.01 | 2 разряда и округление середины |
| USD → KWD | 1.2345 | 1.235 | 3 разряда |
| USD → KZT | 0 | 0.00 | Разрешённая нижняя граница |
| USD → EUR | 100000000000 | 33333333333.33 | Сумма рассчитана до округления отображаемого курса `0.3333333333` |

Почему выбран: представители разных правил точности; обычные целые суммы не выявляют эти ошибки. Количество дробных разрядов смотреть в исходном JSON, а не в форматированном представлении REST-клиента.

После проверки восстановить реальные курсы: выполнить `UPDATE exchange_rate SET fetched_on = CURRENT_DATE - 1;` и отправить основной запрос при доступном интернете. Убедиться, что набор снова загружен сегодня.

## TC-05. Первая загрузка, нормализация и повторный запрос

Предусловие: источник доступен; выполнить `DELETE FROM exchange_rate;`.

Шаги: отправить основной запрос; проверить таблицу и сохранить результат SELECT. Отключить интернет, повторить запрос и сравнить ответ и таблицу. Восстановить интернет.

Ожидается: оба ответа 200 с одинаковыми курсом, суммой и датами. В БД есть USD и KZT, все `fetched_on=T`; USD содержит `rates[KZT]`, KZT — 1. Если источник публикует RUB, его котировка равна `rates[KZT]/rates[RUB]` с 18 знаками. Второй запрос работает без интернета и не меняет набор. Точное число внешних HTTP-запросов этот стенд не измеряет.

Почему выбран: проверяет всю цепочку HTTP → JSON → нормализация котировок USD → запись → чтение.

## TC-06. Обновление устаревших, неполных и несогласованных данных

Предусловие: источник доступен. Перед каждым вариантом восстановить свежий полный набор основным запросом; для гарантированной загрузки предварительно очистить таблицу.

Шаги: выполнить один SQL-вариант ниже, затем основной запрос и проверку БД. Повторить для остальных вариантов:

```sql
-- Вариант 1: вчерашняя загрузка и изменённый курс.
UPDATE exchange_rate SET fetched_on = CURRENT_DATE - 1;
UPDATE exchange_rate SET kzt_per_unit = 100 WHERE currency_code = 'USD';

-- Вариант 2: один из нужных курсов отсутствует.
DELETE FROM exchange_rate WHERE currency_code = 'KZT';

-- Вариант 3: даты публикации двух нужных курсов различаются.
UPDATE exchange_rate SET rate_date = rate_date - 1 WHERE currency_code = 'KZT';
```

Ожидается в каждом варианте: ответ 200 по обновлённым котировкам; восстановлены полный набор, отсутствующий KZT, реальные значения USD/KZT и одинаковые `rate_date=D`, `fetched_on=T`. Старое изменённое значение USD не используется в расчёте.

Почему выбран: три независимых условия обновления, включая защиту от расчёта по старому или смешанному набору.

## TC-07. Дата публикации раньше даты загрузки

Предусловие: свежий полный набор в БД. Чтобы не ждать публикации с прошлой датой, задать согласованные даты вручную:

```sql
UPDATE exchange_rate SET rate_date = CURRENT_DATE - 1, fetched_on = CURRENT_DATE;
```

Шаги: отключить интернет, выполнить основной запрос и проверить даты. Восстановить интернет; выполнить `UPDATE exchange_rate SET fetched_on = CURRENT_DATE - 1;` и основной запрос для восстановления реального набора.

Ожидается при отключённом интернете: 200, `rateDate=T−1`, `fetchedOn=T`; значения и даты в БД не меняются.

Почему выбран: дата публикации сама по себе не делает сегодняшний загруженный набор устаревшим, например в выходной.

## TC-08. Валидация и ошибки ввода

Предусловие: свежий набор в БД. Для каждого варианта менять только указанные поля основного запроса.

Шаги и ожидаемые результаты:

| Вариант ввода | Ожидается |
| --- | --- |
| Удалить по очереди `from`, `to`, `amount`; передать null или пустой код | 400 `INVALID_REQUEST` |
| amount=-0.01; затем 1000000000000000000; затем 0.000000001 | 400 `INVALID_REQUEST` |
| Повреждённый JSON `{broken`; from={}; amount="wrong" | 400 `INVALID_REQUEST` |
| from=`ZZZ`, `000`, `84`, `US1`, `XXX` по очереди | 400 `INVALID_CURRENCY` |
| USD → `840`, amount=999999999999999999.99999999 | 200, сумма `1000000000000000000.00` |

Во всех ошибках проверить `Content-Type: application/problem+json`, поле `code` и отсутствие изменений таблицы. Повторить ошибочные запросы при отключённом интернете: они должны вернуть те же 400. Затем восстановить подключение.

Почему выбран: обязательность полей, границы 18/8 цифр, ошибки JSON и ISO — разные причины отказа. Верхняя допустимая граница проверяется рядом с запрещёнными значениями.

## TC-09. Валидная валюта без котировки

Предусловие: найти валюту, известную JDK, но отсутствующую в текущем `rates` источника. Пример — устаревшая ADP с цифровым кодом `020`: сначала убедиться, что в ответе источника нет ADP. Если выбранная валюта опубликована источником, этот вариант неприменим. Очистить таблицу.

Шаги: отправить `"020"` → USD, 1; проверить ответ и таблицу.

Ожидается: 422 `RATE_NOT_FOUND` в формате ProblemDetail; полный корректный набор поддерживаемых валют сохранён с `fetched_on=T`.

Почему выбран: ведущий ноль должен сохраниться, а отсутствие котировки отличается от неверного ISO-кода.

## TC-10. Недоступность источника и восстановление

Предусловие: полный набор в БД. Выполнить `UPDATE exchange_rate SET fetched_on = CURRENT_DATE - 1;` и сохранить результат SELECT для сравнения.

Шаги: отключить интернет; отправить основной запрос; сравнить таблицу с сохранённой. Восстановить интернет и отправить запрос ещё раз.

Ожидается: первый ответ 503 `PROVIDER_UNAVAILABLE`, таблица целиком сохранена, старый курс не выдан как свежий. После восстановления ответ 200 по текущим котировкам, `fetched_on=T`.

Почему выбран: следующий запрос должен повторить загрузку после сетевого сбоя. Некорректный JSON публичного источника на этом стенде не подменяется; его отклонение проверяется `ExchangeRateApiParserTest` как дополнительная юнит-проверка.

## TC-11. Ошибка записи БД и откат замены

Предусловие: источник доступен, полный набор в БД. В H2 Console выполнить:

```sql
UPDATE exchange_rate SET fetched_on = CURRENT_DATE - 1;
ALTER TABLE exchange_rate ADD CONSTRAINT manual_reject_usd
    CHECK (currency_code <> 'USD') NOCHECK;
```

`NOCHECK` сохраняет существующие строки, но запрещает новую вставку USD. Сохранить результат SELECT.

Шаги: отправить основной запрос; сравнить таблицу. Затем снять ограничение и повторить запрос:

```sql
ALTER TABLE exchange_rate DROP CONSTRAINT manual_reject_usd;
```

Ожидается: первый ответ 503 `DATABASE_UNAVAILABLE`; удаление и частичные вставки откатились, все старые строки и даты сохранены. После снятия ограничения ответ 200, полный набор обновлён.

Почему выбран: реальное нарушение ограничения проверяет откат транзакции после DELETE, а не только сообщение об ошибке. Ограничение снять и при неуспешном выполнении кейса.

## TC-12. Сохранность данных после перезапуска

Предусловие: свежий полный набор в файловой БД; сохранить результат SELECT. Выполнять в пределах одного календарного дня.

Шаги: остановить приложение через Ctrl+C (или Stop в IDE), отключить интернет. Запустить его тем же способом из того же каталога, без дополнительных настроек; отправить основной запрос и проверить таблицу. После проверки восстановить интернет.

Ожидается: 200 с прежними курсом и суммой, таблица и даты совпадают с сохранёнными. Свежие данные используются без доступного источника.

Почему выбран: файловая долговечность не проверяется расчётными юнит-тестами.

## Фиксация результата

Для каждого TC записать дату, версию приложения, входной JSON/SQL, фактический HTTP-статус и тело ответа, изменения БД, состояние интернет-подключения и итог «пройден/не пройден». Если в кейсе несколько вариантов, зафиксировать каждый. Связь с автоматическими тестами приведена в [unit-tests.md](unit-tests.md); совпадение ID не означает, что ручной кейс уже выполнен.
